## ⚠️ Decisions for the spec owner
- **Is an "atomic cut-over" step acceptable under R5? Yes, with one tightening.** R5 asks that every step is testable and leaves the application working. Step 2 ends with typecheck, lint, `core` tests and build green, and the previous audit itself named "one atomic cut-over step" as the fix, so it passes. What it does not do is prove the app works: the migration is only exercised in step 3, and step 3 can force edits to step 2's code. The sentence "Steps 2 and 3 are one atomic change set" then contradicts "step 2 is green". Recommended wording: step 2 is one commit that passes the full gate; step 3 is the pre-merge gate run on that commit (fixes fold into the same PR); Phase 1 never ships without it. Tradeoff: none. Splitting step 2 for smaller commits would need an expand/contract status migration (keep the old values alive, then drop them), which the owner already declined for a pre-1.0 private package.
- **Local ids collide with brief ids again.** The Q7/Q8 collision was fixed, but `A1`/`A2` (local) now sit beside brief `A01`–`A05` (the Problem Statement cites brief "A01"), `N4` (Vitest) beside brief `N04` (the EN version, cited in D07), and `R1` beside brief `R01` (a legal rule), while brief rules are cited unpadded (`R13`, `R15`). Recommended: prefix local ids (for example `L-A1`, `L-N4`, `L-R1`) or pad and cite brief ids as "brief X". Tradeoff: a one-line rename; the portal spec already cites "brief Q06".
- **Accepted deviations (no action):** P2 forward-only `down` against BC §2 "working down", P3 no DB test runner against the checklist's concurrent-case test (replaced by the recorded script), and the single-migration status rewrite against expand/migrate/contract. All are stated in the spec and owner-confirmed.

## 🔍 Gaps
- **Important** — I-1 Step 1 is not purely additive as described. Its tests refer to items that exist only after step 2: "every allowed transition" of the return table (the table is built in step 2), `toReturnStatus` "for every status" (`RETURN_STATUSES` still holds the old five values until step 2), and `overdue(status, …)` "only for `submitted`" (`submitted` is not in the old `ReturnStatus` union, so a signature typed with `ReturnStatus` and comparing against `"submitted"` fails typecheck in step 1). Fix: in step 1 test `defineStateMachine` with a small local table and type `overdue`/`toReturnStatus` over `string`/the generic; move the return-table and nine-status assertions to step 2. This keeps the "step 1 is green on its own" claim true.
- **Important** — I-2 The cut-over wording (see Decisions): step 2 as one commit with the full gate green (`typecheck`, `test`, `lint`, `build`), step 3 as the pre-merge run, and the `.ai/scripts/` script written within the PR (its commit is part of step 3).
- **Important** — I-3 Service method naming contradicts itself: Architecture says `ReturnService.updateStatus` validates then calls `transition`, while step 2 says `updateStatus` is "replaced by `transition`". The portal spec's prerequisite names `transition()`. Pick one service name (suggest `transition(id, status, note?)` on the service, `transition(id, from, to, note)` on the port) and use it in Architecture, step 2, tests and the portal prerequisite.
- **Important** — I-4 `nativeUpdate` and transaction mechanics are underspecified, and three behaviours differ from `flush()`:
  - `updated_at`'s `onUpdate` hook does not run for `nativeUpdate` (it fires only in the unit-of-work change-set computer), so `updated_at` would stay stale. The `nativeUpdate` data must set `updatedAt` and `decisionNote` explicitly.
  - Inside `em.transactional` the callback receives a fork; the repository's own `this.em` is an `orm.em.fork()` without context resolution, so `nativeUpdate`, the event insert and the conflict re-read must all use the callback's em, or the update runs outside the transaction.
  - `nativeUpdate` does not touch the identity map, so the "re-read stored status on zero rows" and the `moved` request must be read with `refresh: true` (or a fresh query), otherwise a managed entity returns the stale status and the 409 carries the wrong `currentStatus`.
  Add these to step 2's repository text and make the step 3 concurrency check assert `currentStatus` in the loser's 409.
- **Important** — I-5 The migration backfill formats RMAs in SQL while the app formats them with `formatRma`; the step 3 list says only "RMA backfill order". SQL `lpad(n::text, 5, '0')` truncates `100000` to `10000`. Fix: the migration reuses the same logic (a TS loop using `formatRma`, `db` may import `core`) or avoids `lpad`; add "backfilled RMA equals `formatRma(seq, created_at)` including a row dated 31 Dec 23:30 UTC" to the scripted run.
- **Important** — I-6 "Join an outer transaction": `em.transactional` defaults to `NESTED`, which opens a savepoint rather than joining. A savepoint works functionally with the portal's `withOrderLock` (advisory-lock transaction, then a transaction-scoped repository), but it is not what the spec says. Specify `propagation: TransactionPropagation.REQUIRED` (join when a transaction exists, else open one) in `create`, and add a test or script case where `create` runs on the portal's transaction-scoped repository once PR A lands.
- **Important** — I-7 State the PATCH success body, the per-phase dependency lines, and the 409 re-read behaviour for `unknown` rows (`allowedTransitions` empty is stated for the list; add `allowed("unknown")` empty to the step 2 test list).
- **Important** — I-8 `apiHandler`'s "sanitised message" is undefined. A driver error message is exactly where bound note values appear, so a sanitised message that still includes message text cannot satisfy the stated oracle. Fix: log `error.name` plus a fixed message (no `error.message`, no stack text containing values), or define the redaction; keep the stated test. Also add P4 to the "confirmed by the owner" sentence.
- **Nice-to-have** — `kind` has no stated TypeScript type (the lab spec's `CLAIM_KINDS` is documentation only here); use the literal `"return"` for now.
- **Nice-to-have** — Catalog rows in the lab spec (state machine, calendar, Timeline, events, reference numbers) match this spec's decisions (P1 amendment present at the events row); no change needed. Portal PR A prerequisites ("agent spec's Phase 1: statuses, RMA, `transition()`, `clock`") are satisfied by Phase 1 as now written, once the name in I-3 is fixed; PR B's `Timeline` props prerequisite is Phase 2 step 1, as stated.
